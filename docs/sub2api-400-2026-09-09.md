# sub2api 400 investigation — September 9, 2026

## Observed failure

The operator reported an upstream `invalid_request_error` with request ID `a7151a92d5568ed5e5b48df5e4aa3981`. The gateway's in-memory log contained four 400 responses on `/v1/messages` for `claude-opus-4-6` and `claude-opus-4-8`, with `stream: true`, `max_tokens: 1024`, no tools, and thinking off. Each had only one upstream attempt. The original log did not retain upstream request IDs, so exact correlation to that ID was not possible.

The locally available sub2api account-test source uses this request shape, including `/v1/messages?beta=true`, a system block, metadata, and Anthropic beta headers. This supports identifying the failures as account connectivity tests; the staged source is not proof of the exact deployed binary's request bytes.

## Confirmed compatibility gaps

Static inspection of the downloaded official 0.0.303 bundle found two missing gateway behaviors:

- The official `Ghn` route builder adds a per-call `x-mirasim-call` ID to relay metadata **before** signing and sealing. The gateway now generates a fresh correlation UUID for each relay call. Device identity and any supplied session identity remain unchanged. Ticket minting does not receive a call ID, and callers cannot inject one through incoming headers.
- The official relay route specifies `dropHeaderValues` for the `oauth-2025-04-20` Anthropic beta token. The gateway now drops that token only for `/v1/messages` to the official relay; other beta tokens and query parameters are retained. Custom upstreams keep their existing header policy.

These changes reproduce official protocol handling. They are **not evidence that either field caused the reported 400**. In particular, the inspected sub2api API-key test path normally does not include the OAuth token, so filtering it may not affect this specific test.

The gateway also records a bounded, validated `upstreamRequestId` in the authenticated request-log endpoint. It takes the ID from response headers or a JSON `request_id` field without persisting raw errors, prompts, credentials, or full response bodies. Existing upstream error responses are still returned unchanged; a 400 is not retried across accounts.

## Initial live diagnostic limit

With explicit approval, a minimal baseline request was sent using the same account identified in the failed gateway logs. It returned HTTP **429**, `rate_limit_error`, request ID `cda79f720c63409594d5b672c8e0e859`. The planned second comparison was not sent. No alternate account was used.

That result does not prove the original 400 is fixed or that the model is unavailable. It blocks a useful live before/after comparison until the account is allowed to send another request. The adapter does not retry this diagnostic through the pool or attempt to bypass the limit.

- unchanged custom-upstream header handling;

- safe request-ID capture without raw prompt/error retention;

## Follow-up: confirmed temperature rejection

The subsequent request ID `b58a9731bb2c39f5b6124f0a4604ea6f` matched exactly one gateway log entry at September 9, 2026, 10:17:22.360 UTC: `/v1/messages`, model `claude-opus-4-8`, `max_tokens: 1024`, streamed, no tools, thinking off, one upstream attempt.

The original account's `/v1/limits` response was 200. Its overall usage windows were not exhausted, but `7d_claude` was: used `35137.19325`, budget `35059`. The reported reset time was September 15, 2026 at **07:55:10 UTC / 15:55:10 China Standard Time**. A healthy overall window therefore did not mean this account could generate Claude responses.

With explicit approval, bounded comparisons used only that same original account and synthetic sub2api-style test content. No account switching occurred. The initial four comparisons each changed at most one request field; a second, separately approved comparison removed only `temperature`. All other body fields, the model, and beta/query behavior were retained for each labeled comparison except the named change. Request signing nonces and call IDs were freshly generated as usual.

Testing stopped at that 429. This isolates `temperature: 1` as a trigger for the request-format rejection in the reproduced request; the account's independently confirmed quota exhaustion prevents successful generation. It does not establish that every other possible request field will be accepted once quota is available.

### Fix

The previous normalization explicitly allowed `temperature: 1`. It now removes `temperature` on the official Mirasim `/v1/messages` leg **before** device signing and metadata sealing, regardless of whether thinking is enabled. This also covers Chat and Responses requests translated into Messages. Existing system blocks, metadata, beta/query behavior, token budgets, and explicit thinking choices remain intact. Custom upstream behavior and non-Anthropic OpenAI requests are unchanged.

Regression tests reproduced the problem before the fix: native and converted requests carrying `temperature: 1` received simulated 400 responses. After the fix, **81/81 related tests pass**, including the original sub2api streaming cases, both affected Opus model names, Chat/Responses conversion, and non-target route preservation.

The full suite passes **211/212 tests**, with only the previously documented expired quota-date fixture failing. The temperature fix was deployed by restarting the systemd service on September 9, 2026 at **18:44:23 China Standard Time**. The service reports `active/running`, the local login page returns 200, and an unauthenticated model-list request returns 401. No post-deployment generation test was sent to the exhausted account.

### Remaining quota requirement

The format rejection and the model-scoped quota are separate problems. This patch addresses the reproduced format error; it does not reset quotas, bypass limits, or prove successful generation on the exhausted account. A successful live generation check still requires available authorized Claude quota. Repeatedly retrying the exhausted account is not a remedy.
