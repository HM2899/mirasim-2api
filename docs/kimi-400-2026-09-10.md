# Kimi 400 in Claude Code and Codex — September 10, 2026

Historical note: the September 11 reasoning-passthrough change supersedes the reasoning omissions described here. Passthrough mode now maps explicit effort settings and preserves returned Chat reasoning through the bridges; it does not assert that the live relay supports every forwarded effort name. See README's Reasoning Passthrough section. The endpoint/model-id fixes below remain in place.

## Reported failure

Kimi models answered `400 The request was rejected as invalid.` in Claude Code and Codex. The
same models answered normally on `/v1/chat/completions`.

## Cause

The relay serves each agent on exactly one wire format. The official 0.0.303 bundle carries the
table:

| Agent | Wire format | Alternate formats |
| --- | --- | --- |
| `claude` | `anthropic-messages` | `chat-completions`, `responses` |
| `codex` | `responses` | `chat-completions` |
| `dsh` | `chat-completions` | none |
| `kimi` | `chat-completions` | none |

The desktop client reaches Kimi by launching the Kimi Code CLI against a local proxy, which
prefixes `/v1` and forwards to the relay — so relay-side Kimi traffic only ever arrives at
`/v1/chat/completions`. Nothing in the bundle sends a Kimi request anywhere else.

This gateway routed by the caller's protocol instead of by the model's upstream. A Claude Code
request went to `/v1/messages` and a Codex request to `/v1/responses`, both carrying
`x-mirasim-agent: kimi`, so both reached an endpoint that agent is not served on. The refusal is
the relay's, and it does not depend on the request's content — which is why no prompt, tool set,
or parameter change made a difference. Only `/v1/chat/completions` callers were unaffected,
which matches the report.

A second, independent refusal shares the same message. The relay knows one Kimi id, `kimi-k3`.
The desktop client's catalog shows `kimi-code/k3` and rewrites it to `kimi-k3` before signing;
the unrewritten name is refused the way a name that does not exist is refused. This gateway
advertised `kimi-code/kimi-for-coding`, `kimi-code/kimi-for-coding-highspeed`, `kimi-code/k3`,
and `kimi-code/k3-256k` under `MIRASIM_RELAY_AGENTS=kimi`, so a client configured from that list
was refused on any endpoint.

Both findings come from static inspection of the vendored 0.0.303 bundle and from this
deployment's own stored state. They were not confirmed against a live relay: no diagnostic
request was sent.

## Supporting local evidence

- The deployment's stored model health lists `kimi-k3` as `healthy`, HTTP 200, discovered from
  the relay's live `GET /v1/models` on September 9, 2026, with `/v1/limits` reporting it
  available. The relay does serve Kimi; `src/config.js` said otherwise and now says this.
- `.runtime/model-probe-results.json` (August 8, 2026) records `kimi-k3` answering
  `400 The request was rejected as invalid.` — the operator's exact string — and
  `.runtime/model-probe-retry.json` records it answering 200 on the chat-completions path.

## Fix

`relayWireFor(model)` reports the endpoint a model's upstream is served on, and the router uses
it in place of the caller's protocol:

- `/v1/messages` with a chat-completions model is translated to a chat-completions request, sent
  to `/v1/chat/completions`, and the answer translated back to Anthropic Messages — streamed and
  non-streamed, tool calls included.
- `/v1/responses` and `/backend-api/codex/responses` with such a model reuse the existing
  Responses-to-chat translation, then answer from the chat upstream through the existing
  Responses forwarders.
- `/v1/chat/completions` is unchanged.

The request bridge follows the official client's own, block for block: the same message folding,
tool shapes, image handling and dropped server-side tools. `thinking`, `output_config`,
`metadata` and the cache breakpoints are left behind because chat completions has nowhere to
carry them, and an unexpected field draws the same bare 400 as the wrong endpoint. Reasoning does
not cross in either direction — the OpenAI protocol has no field for an Anthropic thinking block,
and Anthropic accepts one back only with the signature it issued itself. No `reasoning_effort` is
sent: nothing available here establishes that the relay accepts the field on the Kimi leg, and
the cost of guessing wrong is the refusal this patch exists to remove. Kimi therefore runs at its
own default level on the bridged paths.

`kimi-k3` is now the only Kimi id advertised, and the four desktop labels plus bare `k3` are
aliases resolved before signing, so a client already configured with one keeps working. The
router's shared pass-through is gone: every proxied path now answers explicitly, because which
endpoint a request goes to depends on a model that a shared pass-through cannot see.

The console's request log reads tool calls off a chat-shaped answer as well as an Anthropic one;
without that a bridged turn would show no called tools whether or not the model called any.

## Coverage

`test/relay-chat-bridge.test.js` covers the Claude Code and Codex paths end to end: upstream URL
and agent header, the translated request body, the Anthropic answer and its usage arithmetic, a
streamed answer's full event sequence with a fragmented tool call, the model alias, a tool-result
round trip, an upstream refusal returned in Anthropic error shape, and a Claude model still
reaching `/v1/messages` untranslated. Six of the seven fail against the unpatched gateway; the
Claude regression guard passes both ways.

Full suite: **221/222 pass**. The one failure is the pre-existing quota-window fixture in
`test/dashboard.test.js` whose hard-coded reset date has passed, documented in
`docs/mirasim-0.0.303.md`.

## Not addressed

`/v1/messages` with a `gpt-*` model has the same shape of problem — Codex is served on
`/v1/responses` — and would need an Anthropic-to-Responses request translation that does not
exist here. It was not reported and is not part of this patch. Nothing here changes account
entitlement, model availability, or quota: a fixed request shape does not make an exhausted
account serve one.
